# s07 - Task System（持久化任务图）

## 核心洞见
**状态不能住在 context 里，不管什么格式（包括 JSON 摘要）。**
context 会被压缩，压缩后的摘要是叙事不是结构化数据，无法精确追踪进度。
`.tasks/*.json` 文件存在磁盘上，context 怎么变都不影响它。

---

## 数据结构

```json
{
  "id": 2,
  "subject": "写重构方案",
  "description": "",
  "status": "pending",
  "blockedBy": [1],
  "blocks": [3],
  "owner": ""
}
```

- `blockedBy`：我能开始前，这些任务必须完成
- `blocks`：我完成后，这些任务会被解锁
- 两个字段**双向维护**：加依赖时同时写双方文件

### 为什么 blockedBy 和 blocks 都要存？
只存 `blockedBy` 也能工作（扫全部文件找谁依赖我），但：
- `blockedBy` 用于：开始前检查"我能不能开始"
- `blocks` 用于：O(k) 查询"我完成后能解锁谁"（k = 下游数，不需要扫全部文件）

---

## 核心流程

### Agent 执行循环

```
规划阶段:
  task_create("任务A") → id=1
  task_create("任务B") → id=2   ← LLM 从返回值拿到 id
  task_create("任务C") → id=3
  task_update(1, addBlocks=[2])  ← create 完再建关系（此时才有所有 id）
  task_update(2, addBlocks=[3])

执行阶段（循环）:
  task_list()   → 找 blockedBy=[] 且 pending 的任务，选 id
  task_get(id)  → 拿完整描述，开始干活
  ... 执行 ...
  task_update(id, status="completed")  → 自动触发 _clear_dependency
  task_list()   → 看下一个可执行的任务
```

### _clear_dependency 做了什么
任务完成时，扫描所有 task 文件，把已完成的 id 从别人的 `blockedBy` 里删掉。
→ `blockedBy == []` 的任务自动变为可执行状态。

---

## 工具职责分工

| 工具 | 时机 | 作用 |
|------|------|------|
| `task_create` | 规划阶段 | 建任务，返回 JSON（含 id）给 LLM 用 |
| `task_update` | 规划后 / 执行后 | 建依赖关系 / 更新状态 |
| `task_list` | 每轮开始 | 宏观看进度，选下一个可执行任务 |
| `task_get` | 选定任务后 | 拿完整描述，开始执行 |

---

## 局限与取舍

| 问题 | 原因 | 生产环境解法 |
|------|------|-------------|
| 任务多了慢 | `_clear_dependency` O(n) 扫所有文件 | 数据库索引 |
| 不支持并发 | 无文件锁，多 agent 同时写会覆盖 | 数据库事务/锁 |
| 无错误恢复 | 任务失败没有 retry/rollback | 状态机 + 重试机制 |

## ⚡ 发现的 Bug 与优化（已修复）

### Bug 1：`addBlockedBy` 没有双向维护

**问题：** `addBlocks` 会同时更新双方，但 `addBlockedBy` 只更新当前任务的 `blockedBy`，不反向更新上游任务的 `blocks`。导致 `blocks` 列表不完整。

**修复：**
```python
if add_blocked_by:
    task["blockedBy"] = list(set(task["blockedBy"] + add_blocked_by))
    # 新增：反向更新上游任务的 blocks
    for blocking_id in add_blocked_by:
        blocking = self._load(blocking_id)
        if task_id not in blocking["blocks"]:
            blocking["blocks"].append(task_id)
            self._save(blocking)
```

---

### Bug 2：`_clear_dependency` 没有利用 `blocks` 字段

**问题：** 原版扫所有文件 O(n)，但 `blocks` 已经记录了"我阻塞谁"，完全可以直接用。

**原版 O(n)：**
```python
def _clear_dependency(self, completed_id: int):
    for f in self.dir.glob("task_*.json"):  # 扫所有文件
        task = json.loads(f.read_text())
        if completed_id in task.get("blockedBy", []):
            task["blockedBy"].remove(completed_id)
            self._save(task)
```

**优化版 O(k)（k = 下游任务数）：**
```python
def _clear_dependency(self, completed_id: int):
    completed = self._load(completed_id)
    for blocked_id in completed.get("blocks", []):  # 直接用 blocks
        blocked = self._load(blocked_id)
        if completed_id in blocked["blockedBy"]:
            blocked["blockedBy"].remove(completed_id)
            self._save(blocked)
```

**注意：** Bug2 的修复依赖 Bug1 先修复 —— `blocks` 必须完整，O(k) 优化才成立。

---

### 性能测试结果（固定 k=2，增大 n）

| n（总任务数） | 原版 O(n) | 优化版 O(k) | 提速 |
|---|---|---|---|
| 100 | 1.7ms | 0.16ms | ~10x |
| 1000 | 13ms | 0.15ms | ~83x |
| 5000 | 70ms | 0.15ms | ~480x |

优化版耗时几乎不随 n 变化，n 越大提速越显著。

## 疑问点（已解答）

- **为什么 create 返回 JSON？** → 返回给 LLM，LLM 需要从 tool result 里拿到新任务的 id
- **为什么 addBlocks 不在 create 时设定？** → create 时还不知道其他任务的 id，需要全部 create 完再建关系
- **为什么不用高 token 摘要替代文件？** → 摘要是自然语言，模糊；文件是结构化 JSON，精确可查询；且文件不在 context 里，不会被压缩
