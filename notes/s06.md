# s06: Context Compact 知识点

> 格言：*"上下文总会满，要有办法腾地方"*
> 核心 insight：**不是记住一切，而是知道该忘什么。**

---

## 问题根源

### 为什么 context 会爆？

一个 coding agent 每轮把 response 追加到 messages，下轮把完整 messages 传给 LLM。

```
ls 输出：          ~50 tokens
10 × read_file：   10 × 1200 = 12,000 tokens
系统提示：         ~50 tokens
用户 query：       ~20 tokens
assistant 消息：   ~500 tokens
──────────────────────────────
总计：             ~12,620 tokens（仅一个小任务）
```

**关键矛盾**：第 10 次调用时，第 1 次 read_file 的结果还躺在 messages 里——但它早就没用了。

> tool result 是 context 膨胀的主要来源，也是最安全的压缩对象——因为它的价值是一次性的。

### 什么可以忘，什么必须保留？

| 可以忘 | 必须保留 |
|--------|----------|
| 旧的 tool result 原文 | 所有 assistant 消息（推理、决策） |
| 中间过程细节 | 所有 user 消息（任务目标） |
| 已处理完的文件内容 | 最近几条 tool result（当前上下文） |

## 三层压缩流水线

```
每轮 LLM 调用前：

Tool 结果
    │
    ▼
Layer 1: micro_compact（每轮静默执行）
  把超过最近 3 条的 tool_result 替换成 "[Previous: used {tool_name}]"
    │
    ▼
tokens > 50000？
   否 → 继续
   是 → Layer 2: auto_compact（自动触发）
         把完整对话存到 .transcripts/
         调 LLM 生成摘要
         用 [摘要] 替换全部消息
               │
               ▼
         Layer 3: compact tool（手动触发）
           模型主动调用 compact 工具
           逻辑与 auto_compact 完全相同
```

| 层级 | 触发时机 | 做什么 | 代价 |
|------|----------|--------|------|
| micro_compact | 每轮必做 | 截断旧 tool 结果 | 极低，原地替换 |
| auto_compact | tokens 超阈值 | 全量摘要+重置对话 | 一次 LLM 调用 |
| compact tool | 模型主动判断 | 同 auto，但模型决策 | 同上 |

## Layer 1：micro_compact 数据流

### 消息列表结构（两层嵌套）

```
messages = [
  {role:"user",      content: "读所有文件"},                           ← 普通文本，跳过
  {role:"assistant", content: [{type:"tool_use",  id:"id_1", name:"read_file"}]},
  {role:"user",      content: [{type:"tool_result",tool_use_id:"id_1", content:"...1200tokens..."}]},  ← 找到！
  {role:"assistant", content: [{type:"tool_use",  id:"id_2", name:"bash"}]},
  {role:"user",      content: [{type:"tool_result",tool_use_id:"id_2", content:"...800tokens..."}]},   ← 找到！
  ...
]
```

**定位一个 tool_result 需要两个坐标**：
- `msg_idx`：第几条消息
- `part_idx`：这条消息的 content 里第几个 part

但压缩时 `msg_idx`/`part_idx` 没用到——`part` 是字典引用，直接改就改了原数据。

### 控制流

```
micro_compact(messages)
        │
        ▼
扫描所有 messages
找出 role=="user" 且 content 里有 type=="tool_result" 的 part
收集成：tool_results = [(msg_idx, part_idx, part), ...]
        │
        ▼
len(tool_results) <= 3？
   │                │
  yes               no
   │                │
  return            ▼
(不压缩)    建 tool_name_map：
            扫描 assistant 消息里的 tool_use block
            {"id_1": "read_file", "id_2": "bash", ...}
                    │
                    ▼
            to_clear = tool_results[:-3]（旧的，要压缩）
            保留     = tool_results[-3:]（最近3条）
                    │
                    ▼
            对每条旧 result：
            content 长度 > 100？
               │           │
              no           yes
               │           │
             跳过          ▼
                    result["content"] = "[Previous: used read_file]"
                    （原地修改，messages 自动更新）
```

### 关键问题解答

**Q：为什么 tool_result 在 role:"user" 的消息里？**
A：API 协议规定。工具在你的代码里执行，结果是「你」回传给模型的，所以角色是 user。

**Q：为什么不直接清空 content，而是写 "[Previous: used xxx]"？**
A：两个原因：
1. 模型看到空内容会困惑，以为工具调用失败
2. API 要求 tool_use 和 tool_result 必须成对，不能删 tool_result，只能替换 content

**Q：为什么要建 tool_name_map，不直接去 assistant 消息里找？**
A：tool_result 里只有 id，没有 name。name 在 assistant 消息的 tool_use block 里——两个在不同消息里，需要桥接。
- 直接查：每个 result 都扫全部 messages → O(n²)
- 先建 map：扫一遍，之后每次 O(1) → O(n)

## Layer 2：auto_compact 数据流

```
输入：messages（完整历史，可能很长）

Step 1：保存 transcript 到磁盘
  TRANSCRIPT_DIR / f"transcript_{timestamp}.jsonl"
  每条 message 一行 JSON

Step 2：调 LLM 做摘要
  发给 LLM：conversation_text[:80000]（截断防超长）
  Prompt 要求：1) 做了什么 2) 当前状态 3) 关键决策
  max_tokens=2000

Step 3：替换所有消息
  return [
    {"role": "user",      "content": "[摘要内容]"},
    {"role": "assistant", "content": "Understood. Continuing."},
  ]

输出：只有 2 条消息的新列表
```

**为什么返回 2 条（user + assistant）而不是只有 1 条？**
模型需要看到 assistant 历史才有连贯感。假的 "Understood" 回复告诉模型：我已读过摘要，可以继续工作了。

**已知 Bug**：压缩后最后一条是 assistant 消息，下一轮 API 调用会报错：
```
The conversation must end with a user message.
```
修法：在返回列表末尾加一条 `{"role": "user", "content": "Please continue."}`

## Layer 3：compact tool

**触发方式**：模型主动调用 `compact` 工具（而不是代码判断）。

```python
# agent_loop 里的处理逻辑
if block.name == "compact":
    manual_compact = True
    output = "Compressing..."   # 先给个 tool_result（API 要求成对）

# 工具执行完，消息追加后
if manual_compact:
    messages[:] = auto_compact(messages)   # 同 Layer 2，逻辑完全一样
```

**细节**：`"Compressing..."` 作为 tool_result 追加进 messages，压缩时跟着一起被清掉，无所谓。

## 设计权衡

### KEEP_RECENT = 3 怎么定？

```
KEEP_RECENT 大  →  保留更多历史，模型不容易失忆，但 token 消耗更多
KEEP_RECENT 小  →  token 省了，但模型容易忘，可能重复工作
```

**实测副作用**：旧 read_file 结果被替换成占位符后，模型不知道读过哪个文件，会重新去读——token 反而更多。适合「读完就不用再看」的任务，不适合「需要反复参考多个文件」的任务。

### token 估算准不准？

```python
def estimate_tokens(messages: list) -> int:
    return len(str(messages)) // 4
```

不精确：
- `str(messages)` 带上结构符号（`'role'`, `{`, `[` 等），高估
- 中文字符误差更大
- `// 4` 只是英文文本经验值

但够用——这里只是判断「有没有超阈值」，差 20% 无所谓。精确计数需要额外 API 调用，成本不值得。

### 会不会递归崩溃？

auto_compact 压缩后 messages 只剩 ~2000 tokens，远低于 50000 阈值，不会再触发，不存在递归崩溃。

### `messages[:] =` vs `messages =`

```python
history = []
agent_loop(history)   # 函数内 messages 和 history 指向同一个列表对象

# 函数内：
messages = auto_compact(...)    # messages 指向新列表，history 还是旧的 → 压缩没生效
messages[:] = auto_compact(...) # 原地替换列表内容，history 跟着变    → 压缩生效
```

必须用 `[:]`，否则外部的 `history` 不会更新，下一轮对话还是用旧的完整历史。

---

## 两层压缩的关系

micro_compact 太勤快，会阻止 auto_compact 触发：

```
micro_compact 能处理  →  token 一直低于阈值，auto_compact 不触发
micro_compact 压不住  →  token 超阈值，auto_compact 接管
```

这是设计意图：轻量手段优先，重手段按需兜底。
